# Writing durable specs for AFK agents

A recurring distinction in the workflow skills is HITL (human-in-the-loop) vs
AFK (away-from-keyboard) work, and a bias toward AFK: `to-issues` prefers AFK
slices over HITL "where possible", and `triage`'s whole job is to move issues to
a `ready-for-agent` state where an agent can pick them up cold. Making work
safely AFK-able requires writing specs a different way.

## The spec is a contract that must outlive the codebase

The `triage` agent brief is "the authoritative specification an AFK agent will
work from" — the original issue is mere context. Because a brief may sit unworked
for days while the code moves underneath it, it is written for **durability over
precision**:

- Describe **interfaces, types, and behavioural contracts**, naming specific
  type/function/config shapes the agent should look for.
- **Never** reference file paths or line numbers, and never assume the current
  implementation structure survives — those go stale fast.
- Be **behavioural, not procedural**: say *what* the system should do, not *how*
  to implement it ("`SkillConfig` should accept an optional `schedule` field",
  not "open file X, add a field on line 42"). The agent explores fresh and makes
  its own implementation calls.
- Carry **complete, independently-verifiable acceptance criteria** and
  **explicit out-of-scope boundaries**, so the agent knows when it's done and
  doesn't gold-plate.

The same "no file paths / no code snippets — they go stale" rule governs PRD
implementation decisions (`to-prd`) and issue bodies (`to-issues`). The one
sanctioned exception: a snippet that *encodes a decision more precisely than
prose* (a state machine, reducer, schema, or type shape, ideally from a
prototype) may be inlined, trimmed to the decision-rich part.

## In a Ralph loop the brief is a living scope, not a waterfall doc

When the AFK agent is a Ralph loop (see `autonomous-loops-ralph`), the brief
takes a specific shape: a PRD that doubles as the progress tracker. Anthropic's
structure — each item a JSON object with a `passes: false` field the agent flips
to `true` when done — turns the spec into a living TODO you can edit *mid-flight*
(set `passes` back to false to redo something, add an item even while the loop
runs). You're describing a different end state, not rewriting a linear plan, and
the loop converges on it.

The hard requirement is an explicit **stop condition and scope**. A vague brief
("improve this codebase") invites two failures: the loop never terminates, or it
declares victory early by quietly redefining the goal — Matt's example is a
coverage loop that decided some "internal" commands didn't count and skipped them.
So a durable AFK brief names the files in scope, the edge cases that *do* count,
and exactly what "complete" means, so the agent knows when to emit its completion
sigil. Risky, architecture-shaping work is kept human-in-the-loop and only the
low-risk remainder is handed to the unattended loop.

## A progress file is the brief's memory across runs

Because each loop iteration starts in a fresh context window (an expert who
forgets everything between tasks), a committed `progress.txt` is what lets the
brief outlive a single run: it records what was done, decisions and why, and
blockers, so the next iteration skips re-exploring the repo. Combined with the
git history (commit per feature → clean `git log`, `git diff`, rollback points)
it gives full context without burning tokens on exploration. Like research
assets, it's session-scoped: delete it once the sprint is done rather than let it
rot into stale documentation.

## Disclose AI authorship and preserve resolved knowledge

Two supporting habits keep an AFK pipeline trustworthy. Every comment `triage`
posts is prefixed *"This was generated by AI during triage."* And work resolved
during a grilling/triage session is captured into the brief or the "established
so far" notes so it isn't lost when the session ends — the next agent (or human)
resumes from a written record, not a vanished conversation. Rejected
enhancements are even written to an `.out-of-scope/` knowledge base so a future
triage doesn't re-suggest them.
