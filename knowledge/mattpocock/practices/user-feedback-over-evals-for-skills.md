# Skip evals for skills; listen to user feedback instead

Asked why he doesn't run evals against his skills, Matt gives a direct refusal
with a cost argument, not a dismissal of evals in general: "I don't have a
model provider's worth of tokens to throw at evals." Evals are a
resource-intensive discipline built for an org with model-provider-scale
compute; applying that discipline to a solo skills practice is importing a
cost structure that doesn't fit the budget.

## The maintenance cost would eat the thing evals exist to protect

The second reason compounds the first: "if I did write evals, I'd spend 95%
of my time maintaining them instead of writing skills/shipping." An eval
suite is not a one-time cost — it has to be kept in sync with the skills it
tests, and at solo scale that upkeep would consume the time that's supposed
to go into the actual work (writing and shipping skills). The trade only
makes sense if the eval's signal is worth more than the shipping time it
displaces; for a single practitioner iterating a skill collection, Matt
judges that it isn't.

## Real usage already is the eval

The sharpest part of the argument reframes what an eval is *for*: "evals just
push a bunch of data through your system — similar to users actually using
the skills. So I prefer to listen closely to user feedback instead of trying
to emulate it ahead of time." An eval is a simulation of usage, built to
approximate feedback before the cost of being wrong in front of real users.
When real usage is already available and cheap to listen to, building the
simulation is solving a problem that's already solved more directly —
the substitute is only worth building when the real signal isn't accessible
yet.
