# Greenfield is an illusion; default to treating every codebase as legacy

Matt rejects the greenfield/brownfield split he's regularly asked about — "do
your skills work on greenfield codebases?" versus "legacy codebases?" — as a
distinction that "has never really felt real." A greenfield project isn't
software dropped into an empty void: "there are existing systems to integrate
with, user preferences to work around" from day one. The only thing that
actually differs is how much of the repo's coding-convention and prior-art
scaffolding already exists — not whether outside constraints exist at all.

## Why the window closes fast enough to make the label useless

The sharper point is about *duration*, not definition. Even granting a real
distinction at the moment a project starts, "since code is being produced faster
than ever before, how long does that codebase stay green? Two days? A week at
most?" A codebase accumulates the conventions, integrations, and constraints that
define "legacy" on a timescale of days now, not years — so a label that's only
true for a week isn't a useful category to design a skill's behavior around.
**"All the fields are brown, and being churned up faster than ever."** The
practical corollary: **default posture should be "this is a legacy codebase,"
even if it's a week old** — write skills, conventions, and agent instructions
assuming existing constraints and prior art are already there, rather than
assuming a clean slate that will stop being true almost immediately.

## The edge case that tests the boundary: starter kits aren't automatically brownfield

Asked whether starting from scaffolding code or a starter kit counts as
brownfield, Matt says no — a starter kit supplies structure but not the thing his
own definition hinges on: established conventions earned from real use and
decisions already made under real constraints. Structure alone doesn't make a
repo legacy; accumulated, load-bearing prior art does. That keeps the "default to
brownfield" posture from over-firing on every repo that merely isn't literally
empty — the test is whether real decisions and integrations have accrued, not
whether *any* files exist yet.
